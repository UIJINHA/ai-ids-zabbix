## 모델
- Isolation Forest, contamination=0.01, n_estimators=200
- 학습 데이터: 정상 246샘플 (2026-09-26~10-07, 공격 없는 구간)
- 정상 이상점수 분포: -0.0085 ~ 0.2872
- 모델 파일: model/iforest.pkl, scaler.pkl, feature_cols.json (git 제외)

## Feature (10개 지표 × 평균/최대/표준편차 + 시간 sin/cos = 32컬럼)
cpu_user, load1, mem, net_in, net_out, ssh_fail, ssh_ok, conn, synrecv, proc

## 탐지 방식 (하이브리드)
- **모델**: 자원을 흔드는 공격 (DoS, 채굴, 유출)
- **룰**: 로그에만 흔적이 남는 공격 (무차별 대입, 스캔)
- 최종 등급 = 둘 중 더 심각한 쪽
- 룰 임계: ssh_fail≥30 & ssh_ok<1 → 위험 / synrecv≥20 → 위험
          / net_out_mean≥50MB → 위험, ≥25MB → 경고 (데이터 유출; 정상 상한 ~17MB)
- 모델 임계: score<-0.06 위험, <0 경고 (튜닝 10-07: -0.05→-0.06, ab 정상 CPU버스트 거짓'위험' 제거)

## 핵심 발견 (자소서 재료)
무차별 대입 공격을 모델이 못 잡았다(미탐). detect 시점 Feature를 직접 확인한 결과,
로그인 실패는 평소 0→35로 명확히 증가했으나, 전체 32개 Feature 중 자원 관련 29개가
정상이어서 신호가 희석됨을 확인. 자원을 흔들지 않는 공격은 순수 이상탐지로는 한계가
있어, 로그 지표에 별도 룰을 결합(하이브리드)하여 해결. 이후 재검증에서 정확히 탐지됨.
→ "자원 공격=모델, 로그 공격=룰" 설계가 양쪽 다 입증됨.

채굴형(CPU) 테스트에서 추가 발견: 모델이 가장 강하게 반응한 구간은 CPU가 급등하는
'과도기'(std 큰 15:40~16:00, [위험])였고, CPU가 88%에 일정하게 고정(std≈0, 16:05~)되자
오히려 [경고]로 약해졌다. Isolation Forest가 절대 수준(mean)보다 변동성(std)·순간최대(max)에
더 민감함을 확인. → 느리게 램프업해 일정 수준을 유지하는 은밀한 채굴은 탐지가 약해질 수
있어, 지속시간/누적 기반 룰로 보완할 여지가 있음(향후 과제).

데이터 유출 테스트에서 서사가 한 단계 더 정교해짐: net_out이 평소의 ~200배(+600σ)로
치솟았는데도 모델은 [정상](+0.03)으로 판정(미탐). 무차별 대입과 동일한 "희석" 현상 —
Isolation Forest는 32개 Feature의 평균 고립도로 점수를 내므로, 단일 지표 하나만 극단적이고
나머지 29개가 정상이면 신호가 묻힌다. 즉 한계는 "자원이냐 로그냐"가 아니라
"여러 지표가 동시에 흔들리냐(=모델이 강함: DoS, 채굴 램프) vs 단일 지표만 튀냐
(=모델이 약함: 무차별대입, 대역폭 유출)"였다. 해결책도 동일: 단일 지표 공격엔 명시적 룰.
ssh_fail 룰을 넣었던 것처럼 net_out 룰(≥50MB 위험)을 추가하자 유출이 [위험]으로 정확히
탐지됨 → 하이브리드(모델+룰) 설계가 로그/자원 양쪽의 단일지표 공격 모두에서 입증됨.

## 검증 도구
- `src/eval_attack.py` : 과거 특정 구간을 모델로 재점수화(최근 90분 제한 없이 전체 타임라인 스캔).
  사용: 프로젝트 루트에서 `PYTHONPATH=src python src/eval_attack.py <시작> <끝>` (예: `2026-10-07T15:35:00 2026-10-07T16:45:00`).
  detect_anomaly.py 는 실시간(최근 90분)용, eval_attack.py 는 사후 검증용.
- `src/evaluate.py` : 라벨된 공격 6종에 대해 모델+룰 성능(탐지/미탐/오탐) 측정, results/tuning-log.csv 에 1행 append.
  사용: `PYTHONPATH=src python src/evaluate.py "노트" [DANGER_TH] [WARN_TH]` (임계 오버라이드로 튜닝 실험).

## 튜닝 기록 (results/tuning-log.csv)
- baseline(WARN 0, DANGER -0.05): 탐지 6/6, FP 12건(4.21%)
- FP 원인 규명: 18:05~18:20 '위험'은 gen_traffic ab 버스트(17:57 CPU 99%)를 모델이 이상으로 본 것.
  학습 데이터가 최근 ab 버스트(commit c9c995f)를 과소대표 → 정상인데 -0.052로 튐.
- **적용: DANGER -0.05→-0.06** (탐지 6/6 유지, 거짓 '위험' 제거). 실험상 WARN -0.055까지 내리면
  FP 0.7%지만 과적합 우려로 보류.
- **근본 해결(미완): 재학습** — ab 버스트가 충분히 쌓인 정상 데이터로 모델 재학습하면 이 FP 소멸 예정.
