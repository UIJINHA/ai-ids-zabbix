# 04. 실습 환경 설계 (정상 부하 생성)

## 문제 인식
수집한 데이터를 확인한 결과 감시 대상 서버의 CPU 사용률은
평균 0.27%, 최대 5.12%였고 idle이 평균 99.73%였다.
아무 서비스도 운영하지 않는 서버였기 때문에 지표의 변동이 거의 없었다.

이 데이터로 학습할 경우 두 가지 문제가 예상되었다.

첫째, 정상 데이터의 분산이 0에 가까워 사소한 변동도 이상으로 판단된다.
둘째, 반대로 부하를 일으키는 공격은 지표가 극단적으로 튀기 때문에
고정 임계값 한 줄로도 탐지가 가능해진다.
이상 탐지 모델을 적용할 근거 자체가 성립하지 않는 상태였다.

## 조치
감시 대상 서버를 실제로 서비스가 동작하는 상태로 구성했다.

- VM2에 nginx 설치
- VM1에서 HTTP 요청을 주기적으로 발생 (5분 주기, 시간대별 요청량 차등)
- 정상 SSH 로그인도 확률적으로 발생 (10분 주기)

요청량은 업무 시간대에 많고 새벽에 적도록 구성해 일간 주기를 만들었다.
이로써 같은 CPU 사용률이라도 시간대에 따라 정상일 수도 비정상일 수도 있는
상황이 만들어졌고, 단일 임계값으로는 판단할 수 없는 조건이 되었다.

## 로그인 실패 지표 추가
자원 지표만으로는 SSH 무차별 대입 공격을 탐지할 수 없다.
비밀번호 시도는 CPU나 네트워크에 거의 영향을 주지 않기 때문이다.
그래서 Zabbix UserParameter로 로그 기반 지표를 직접 추가했다.

    security.ssh.failed    최근 5분간 로그인 실패 횟수
    security.ssh.accepted  최근 5분간 로그인 성공 횟수

성공 횟수를 함께 수집한 이유는, 실패 횟수만으로는
정상 사용자의 오타와 무차별 대입 공격을 구분할 수 없기 때문이다.
무차별 대입은 실패가 반복되면서 성공이 없다는 특징을 가진다.

처음에는 에이전트 계정에 로그 읽기 권한이 없어 값이 항상 0으로 조회되었고,
zabbix 계정을 adm, systemd-journal 그룹에 추가해 해결했다.
값이 0으로 조회될 때 실제로 실패가 없어서 0인지 수집이 되지 않아 0인지
확인하기 위해, 의도적으로 로그인을 실패시켜 값이 3으로 변하는 것을 확인했다.

## 기타
VM2의 시간대가 UTC로 설정되어 있어 Asia/Seoul로 변경했다.
공격 발생 시각과 로그를 대조할 때 9시간 차이가 분석 오류로 이어질 수 있다고 봤다.

## 결과
- 2026-09-26 이전 데이터는 부하가 없는 구간이므로 학습에서 제외
- 이후 수집 데이터를 정상 패턴 학습용으로 사용
